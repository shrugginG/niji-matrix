**准入理由（中文）：** ATT&CK 的直接行为是攻击者使被害数据通过加密及密钥不可得而丧失合法可读性，属于影响释放；文件、虚拟磁盘和云对象都可能承载这一状态变化。该父候选值得保留，但单纯“加密后不可用”只描述结果，不能说明匿迹。Niji 父技术应改写为攻击者在实施这种可用性剥夺时，控制加密覆盖方式或加密权限所在的执行面，使早期文件行为、内容统计或主机端点观察与完整、显著的加密流程不同。准入不以勒索字条、强算法或拒绝交出密钥本身作为匿迹证明。独立证据分别来自 SentinelOne Labs 对间歇加密样本的技术观察，以及 AWS CIRT 对被窃有效凭据、SSE-C 和大量 CopyObject 重加密的事件观察。

**Admission rationale (English):** ATT&CK's direct behavior is an adversary making victim data unavailable to legitimate readers through encryption and withheld key access, an Impact outcome that can affect files, virtual disks, or cloud objects. The parent merits inclusion, but “encrypted and unavailable” alone describes an outcome rather than a stealth variable. The Niji parent should adapt the scope to attacker control over encryption coverage or the authority/execution surface that performs encryption, changing early file behavior, content statistics, or host endpoint visibility relative to a conspicuous full encryption run. A ransom note, strong cipher, or withholding a key does not by itself establish stealth. Independent support comes from SentinelOne Labs' technical observations of intermittent encryptors and AWS CIRT's incident observations of stolen valid credentials, SSE-C, and many CopyObject re-encryptions.

**交叉范围（中文）：** T1486 的直接对象是仍存在但在合法密钥上下文中无法读取的内容或对象版本。T1485 的删除与覆盖、T1561 的磁盘内容/结构擦除、T1490 的快照或恢复控制破坏，分别按自身直接状态变化归属；它们可与加密同案共现。正常静态加密、可由组织掌握密钥的计划迁移，以及外传前仅供打包的加密是反例。NJT-0117 已覆盖勒索软件为保持系统连续性而跳过路径、扩展名或整机的选择性排除，故“选择关键对象不加密”不得再作为 T1486 子项。NJS-0111-004 已覆盖 Ragnar Locker 将载荷置于来宾虚拟机跨越宿主传感器边界，故“在虚拟机内加密”本身也不得复制为此处子项。

**Cross-technique scope (English):** T1486's immediate object is content or an object version that remains present but cannot be read under the legitimate key context. T1485 deletion and overwriting, T1561 disk-content or structure wiping, and T1490 snapshot or recovery-control damage are owned by their respective direct state changes; they can co-occur in one incident. Ordinary at-rest encryption, an approved migration retaining organizational key custody, and encryption used only to package exfiltrated data are counterexamples. NJT-0117 already owns selective skipping of paths, extensions, or whole hosts to preserve ransomware operating continuity; “leave critical objects unencrypted” must not be duplicated as a T1486 child. NJS-0111-004 already owns Ragnar Locker's guest-VM placement across the host sensor boundary; “encrypt in a VM” alone must not be duplicated here.

## Parent field-content proposal

**Name / summary:** 为影响而加密数据 / Data Encrypted for Impact. 中文摘要：攻击者令受害数据在合法密钥上下文中不可读，并通过改变加密覆盖或加密权限位置削弱早期发现。 English summary: Adversaries make victim data unreadable under legitimate key custody and reduce early detection by altering encryption coverage or authority location.

**Definition and concept / 定义与概念**

中文：攻击者对原本可供业务读取的数据实施未授权的加密或重加密，并保留、替换或遗失解密所需密钥，使合法用户无法按原业务用途读取当前数据状态。判断重点是可读状态与密钥控制权的变化，而不是有无勒索要求。文件仍可存在、对象键仍可解析、服务仍可响应，但读取结果已无法由组织原有的密钥与工作流还原。加密前的权限取得和部署是前置条件，后续删除备份与阻止恢复是相邻行为。

English: The adversary performs unauthorized encryption or re-encryption of data that business workflows could previously read and retains, replaces, or loses the key needed to decrypt it, denying legitimate users the current data state. Classification rests on the change in readability and key custody, not on a ransom demand. A file can remain present, an object key can still resolve, and a service can still respond while the organization's existing keys and workflow can no longer reconstruct the data. Privilege acquisition and deployment precede this behavior; backup destruction and recovery inhibition are adjacent behaviors.

**Stealth characteristics / 匿迹特性**

中文：常规批量全文件加密容易留下密集写入、扩展名或熵变化及业务不可用。攻击者可只改写文件内部间隔片段，使全文件统计与写入量不像完整密文；也可借已取得的有效云凭据调用存储服务，以攻击者掌握的客户密钥在服务端重加密现有对象，使主机上看不到同等规模的本地文件改写。这两种设计分别稀释内容/写入特征，以及把观察点从端点移至对象数据面，均不消除恶意结果。残余痕迹是同一进程对大量业务文件的异常写入、结构性片段差异，或大量同一主体的 SSE-C 对象重写与版本变化。

English: A conventional bulk full-file encryptor tends to leave dense writes, extension or entropy changes, and business unavailability. An adversary can rewrite spaced regions within each file so whole-file statistics and write volume do not resemble complete ciphertext, or can use acquired valid cloud credentials to have a storage service re-encrypt existing objects under an attacker-held customer key, leaving no equivalent local file-rewrite volume on an endpoint. These designs respectively dilute content/write features and move the observation point from endpoint to object data plane; neither removes the malicious outcome. Residual traces include abnormal business-file writes by one process, structured regional differences, or many SSE-C object rewrites and version changes by one principal.

**Scope boundary / 范围边界**

中文：纳入未经授权、以剥夺合法读取为直接目的的加密状态转换，以及有证据支持的覆盖或权限位置匿迹变量。仅有高熵文件、加密 API 调用、SSE-C 请求或勒索通知都不足以判定本技术；必须验证数据先前可读、当前密钥上下文失配且存在恶意操作链。加密后删除原件可另记数据销毁，但不能把删除痕迹当作加密证据。只改写账户权限导致拒绝访问属于访问控制变化，未发生密文状态转换时不属于本技术。

English: Include unauthorized encryption state changes directly intended to deny legitimate reading and coverage or authority-location stealth variables supported by evidence. A high-entropy file, cryptographic API call, SSE-C request, or ransom notice alone cannot establish the technique; verify prior readability, current key-context mismatch, and a malicious operation chain. Deleting the original after encryption may separately qualify as Data Destruction, but deletion traces do not prove encryption. An access-control change that denies reading without a ciphertext state transition falls outside this technique.

**Application scenarios / 应用场景**

中文：在终端或文件服务器，勒索载荷可按文件片段改写文档或数据库相关文件，使业务打开失败而传统全文件熵阈值不一定明显上升。在云对象存储，攻击者可滥用已泄露的有效凭据，对同一对象调用服务端客户密钥重加密；对象名仍在，合法工作负载却没有攻击者提供的密钥。两种情境都可与横向移动、勒索通知或备份破坏并存，但这些伴随行为不能代替对加密状态的核实。

English: On endpoints or file servers, an encryptor may rewrite spaced regions of documents or database-related files, causing business reads to fail while whole-file entropy thresholds need not rise conspicuously. In cloud object storage, an adversary may abuse exposed valid credentials to invoke server-side re-encryption of existing objects with a customer key they provide; object names remain while legitimate workloads lack that key. Both settings can accompany lateral movement, ransom notices, or backup damage, but those companion behaviors cannot replace verification of the encryption state.

**Attacker model / 攻击方模型**

中文：攻击方需能改写目标文件内容，或具备对目标对象执行有效写入/复制的存储权限，并能控制部分加密布局或提供服务端加密密钥。间歇改写必须在较少字节被改变时仍足以破坏业务解析；服务端重加密必须使组织缺少当前对象版本的客户密钥。攻击方仍承担进程来源、文件访问、API 身份、请求时间和被改写对象集合等可关联痕迹。

English: The adversary needs authority to rewrite target file content or valid storage write/copy rights over target objects, plus control of the regional encryption layout or customer-provided service key. Sparse rewriting must still disrupt business parsing with fewer bytes changed; service-side re-encryption must leave the organization without the current object version's customer key. The adversary still exposes correlatable process lineage, file access, API principal, request timing, and changed-object sets.

**Defender model / 防守方模型**

中文：防守方可能有端点文件事件、进程关联、少量内容抽样、云对象数据事件与版本目录，但这些观察并非天然完整。只有整文件熵或固定短窗写入量的检测会漏看间歇加密；只监控主机端点会漏看服务端对象重加密。防守方需要从业务文件写入者到文件结构变化，或从云主体到对象键、加密参数和版本结果建立关联，并用组织批准的加密任务及密钥归属校准误报。缺失内容采样、未启用 S3 数据事件或合法应用本来使用 SSE-C 时，证据强度要下降。

English: Defenders may have endpoint file events, process lineage, limited content sampling, cloud object data events, and version inventories, but none is inherently complete. Detectors based only on whole-file entropy or short-window write volume may miss intermittent encryption; host-only monitoring misses service-side object re-encryption. Defenders need a join from business-file writer to structural content change, or from cloud principal to object key, encryption parameter, and resulting version, calibrated against approved encryption jobs and key custody. Missing content samples, disabled S3 data events, or legitimate application use of SSE-C lowers evidential strength.

**Mechanism proposals:** `TA0040-T1486-MECH-SPARSE`: `NM-FD` primary, summary zh “保留未加密片段降低整文件密文外观”, en “Preserved plaintext regions weaken whole-file ciphertext appearance”; analysis: altered layout → lower write volume and retained plaintext regions → whole-file entropy/I/O alarms become less discriminating → early encryption may be misclassified, while per-region sampling and process-linked writes remain. Evidence E2; `high` for observed trace change, `medium` for generality across products. `TA0040-T1486-MECH-SERVICE`: `NM-BT` primary, summary zh “服务端重加密移出主机文件观察面”, en “Service-side re-encryption leaves host file-observation scope”; analysis: valid principal invokes SSE-C CopyObject → no comparable endpoint rewrite → host-only detectors see no corresponding file event → object data events and key parameters become decisive. Evidence E3/E4; `high` for AWS case, `medium` for any cross-service generalization. These are two supported causal chains, not a claim that encryption itself is stealth.

**Taxonomy narrative / 分类叙述**

中文：建议两个兄弟项按防守观察被改变的位置划分：文件内覆盖密度改变内容与文件写入特征；存储服务客户密钥重加密改变执行权限和传感器所在域。它们可在同一事件中连续出现，但一个文件只做局部改写不说明使用服务端密钥，SSE-C 重加密也不说明局部改写。算法、扩展名、平台、勒索组织和被加密文件类别都不是划分基础。选择性不处理关键目标归 NJT-0117；来宾隔离归 NJS-0111-004。

English: The proposed siblings divide by where defender observation changes: regional coverage density alters content and file-write features, while service/customer-key re-encryption changes the execution authority and sensor domain. They can occur in the same incident, but sparse local rewriting does not imply a service key, and SSE-C re-encryption does not imply sparse rewriting. Cipher, extension, platform, ransomware family, and target-file category are not partition keys. Selective preservation belongs to NJT-0117; guest isolation belongs to NJS-0111-004.

## Proposed Niji child A: `TA0040-T1486-CHILD-SPARSE`

**Name:** 文件内稀疏加密 / Sparse In-File Encryption. **Confidence:** `high` for child existence and trace mechanism from E2; the exact byte-stride is an implementation, not a taxonomy key.

**Definition / 定义：** 攻击者只加密目标文件中间隔分布的字节区段，同时保留其他区段明文，使文件对原业务程序失效。稳定变量是同一文件内部的改写密度与布局，不是处理哪些文件。 / The adversary encrypts spaced byte regions within each target file while leaving other regions as plaintext, making the file unusable to its original business reader. The stable variable is the density and layout of rewriting *inside* a file, not which files are selected.

**Stealth characteristics / 匿迹特性：** 文件内稀疏加密使整文件保留较多原始内容、写入字节减少，依赖整文件熵或短窗 I/O 峰值的观察较难把它识别为完整加密；被写区段的高熵、原始结构破坏、同一进程跨文件重复的稀疏写入模式仍可见。 / Sparse In-File Encryption preserves more original content and lowers written bytes, making whole-file entropy or short-window I/O spikes less reliable signs of complete encryption. High-entropy modified regions, broken original structure, and repeated sparse-write patterns across files by the same process remain visible.

**Boundary / 边界：** 一般分块加密、压缩、数据库正常页写入和仅跳过系统目录都不满足此项。需证明被攻击文件先前可用、区段被未授权密文替换、保留区段与被改写区段并存且业务读取失败。跳过整个文件或目录的决策另归 NJT-0117。 / Ordinary chunked encryption, compression, normal database page writes, and skipping a system directory do not qualify. Establish prior usability, unauthorized ciphertext replacement of regions, coexistence of preserved and changed regions, and failed business reading. A decision to skip an entire file or directory belongs to NJT-0117.

**Scenario / 场景：** 勒索进程在文件服务器上改写每个被选业务文件的间隔区段，仍能快速造成文档或数据库片段不可读；端点日志可能只显示较低写入字节率，但多个不同目录的文件由同一进程被改变。 / An encryptor rewrites spaced regions in each selected business file on a file server, quickly making documents or database segments unreadable. Endpoint logs may show a lower byte-write rate, while the same process still changes files across multiple directories.

**Attacker / 攻击方：** 需要内容写权限、能够识别足以使文件解析失败的区域，并承担对每个文件反复读写的进程痕迹；过低覆盖可能无法造成所需影响。 / The adversary needs content-write authority and enough file-format or empirical knowledge to alter regions that disrupt parsing; repeated per-file read/write process traces remain, and too little coverage may fail to cause intended impact.

**Defender / 防守方：** 关联同一进程对多个业务文件的修改，再抽样比较修改前后区域熵、文件头和可解析性；整文件 SHA 值与扩展名变化只能作辅助，不能代替区段证据。缺少内容保留或主机未受管时只能得出行为可疑，不能证明稀疏布局。 / Correlate one process modifying many business files, then sample before/after regional entropy, file headers, and parseability. Whole-file hashes and extension changes are adjuncts rather than proof of regional layout. Without retained content or managed-host visibility, defenders can flag suspicious behavior but cannot prove sparse structure.

**Mechanism:** `NM-FD` primary with E2, as above. **Research limitation / 研究限制：** SentinelOne Labs documents several families and specific regional patterns; it does not prove every partial overwrite is malicious or quantify a universal detector threshold. Regional sampling needs a safe prior version or controlled canary and may be costly on large files. / SentinelOne Labs documents several families and particular regional patterns; it does not prove every partial overwrite is malicious or establish a universal threshold. Regional sampling requires a safe prior version or controlled canary and can be expensive for large files.

**Mechanism:** `NM-BT` primary with E3/E4. **Research limitation / 研究限制：** AWS CIRT 报告确认恶意大规模 SSE-C 覆写，但不公布每个受害环境的可读性测试结果或完整攻击时序；应把“当前版本无组织密钥”作为需核实的病例事实。启用版本控制或对象锁可能保留旧版本，不能据此说攻击没有造成当前版本影响。 / AWS CIRT confirms malicious mass SSE-C overwrites but does not publish every victim's read-test result or full timeline; treat lack of organizational key for the current version as a case fact to verify. ## Defense design, target-specific and implementable

### `TA0040-T1486-DET-ENDPOINT` / `TA0040-T1486-NJA-ENDPOINT`

**Strategy:** detect process-linked loss of readability across multiple business files, including low-write/partial encryption, targeting parent and sparse child; domain `enterprise`, Windows first implementation. **Analytic logic:** ingest `DeviceFileEvents` file create/modify/rename events; group by `DeviceId`, `InitiatingProcessUniqueId` (or process ID plus creation time), and a moving 15-minute investigative window. Distinct changed business paths across more than one directory, an unusual writer for those directories, and canary or retained-version comparison promote a candidate. For candidate files, a file-integrity/content sensor measures modified-byte share and regional entropy/format-parse failure; keep these fields in a separate sensor source, because `DeviceFileEvents` does **not** promise them. Sparse high-entropy changed regions coexisting with preserved plaintext plus failed application read promote sparse-child confidence. Tune counts against per-host legitimate backup, sync, database, and bulk-edit jobs; thresholds are environmental hypotheses, not source facts. Do not require ransom note, new extension, full-file high entropy, or precursor backup deletion. **Required fields:** from DeviceFileEvents: `Timestamp`, `DeviceId`, `ActionType`, `FolderPath`, `FileName`, `InitiatingProcessUniqueId`, `InitiatingProcessAccountName`, `FileSize`, optionally `PreviousFileName` and `RequestProtocol`; from content/file-integrity sensor: file identifier, before/after version handle, changed offset ranges, sampled regional entropy or magic/parse result. **Observables:** unusual breadth of file modification by one writer; repeated changed-region pattern; read failure. **False positives:** approved encryption migration, backup restore, synchronization, software build, database compaction, legitimate rekeying. **Blind spots:** unmanaged file server, unsupported share provenance, no prior content/version, encrypted-at-rest business files, payload modifying virtual disks below file-level view. **Evidence:** E2 for sparse behavior; E5 for Microsoft schema; E6 for controlled-folder authority/mitigation; E1 for T1486 detection scope. An EDR-only analytic may detect broad writes but cannot assert regional sparsity without the added sensor.

**策略：** 发现同一进程使多个业务文件失去可读性，包括低写入量的局部加密；覆盖父级和稀疏子项，先在 Windows 实施。**分析：** 用文件事件按设备、进程唯一键和可调 15 分钟窗口聚合不同目录的业务文件修改，并与批准写入程序基线比较；对候选文件使用另一个内容/完整性传感器比较前后版本、被改写偏移、区域熵和解析结果。若密文区段与保留明文区段共存且应用读取失败，提高稀疏子项置信度。Microsoft 的 DeviceFileEvents 不提供区域熵或改写偏移，不能把它们伪称为已有字段。正常备份、同步、软件构建、数据库整理与合法重加密会误报；无受管主机或前版本时只能告警批量写入，不能断言局部布局。

### `TA0040-T1486-DET-OBJECT` / `TA0040-T1486-NJA-OBJECT`

**Strategy:** detect unauthorized service-side re-encryption of existing object keys with customer-provided keys, targeting parent and service child; `enterprise`, `IaaS`. **Analytic logic:** enable CloudTrail S3 *data events* for write APIs on protected buckets. Filter `eventSource=s3.amazonaws.com`, `eventName=CopyObject` (also inspect `PutObject` and `CreateMultipartUpload` as related writes), and nonempty `requestParameters.x-amz-server-side-encryption-customer-algorithm`. Join `userIdentity.arn` or `accessKeyId`, `sourceIPAddress`, `requestParameters.bucketName`, `requestParameters.key`, `eventTime`, and `responseElements.x-amz-version-id` where present. Over a configurable 10–30 minute investigative window, count distinct existing keys rewritten by one principal, compare its SSE-C use and bucket scope to an approved workload/job registry, and escalate bursts or first-seen use. Confirm whether the current versions are inaccessible to authorized readers and whether prior versions remain. Do not log key material. **Required fields:** `eventTime`, `eventSource`, `eventName`, `userIdentity.arn`/`accessKeyId`, `sourceIPAddress`, `requestParameters.bucketName`, `requestParameters.key`, `requestParameters.x-amz-server-side-encryption-customer-algorithm`, `responseElements.x-amz-version-id` if versioned, plus protected-bucket inventory and approved-principal baseline. **False positives:** scheduled approved SSE-C rekeying, migration, restoration, bulk copy. **Blind spots:** data events disabled or scoped away, delayed event delivery, approved principal compromised, client-side encryption uploaded without SSE-C parameter, legitimate SSE-C makes key ownership an out-of-band question. **Evidence:** E3 for actual incident and exact parameter, E4 for data-event fields, E7 for version behavior. The same strategy objective could include multiple analytics later, but this analytic has its own data plane logic and must not be merged with endpoint file analytics.

**策略：** 发现已有对象被客户提供密钥在服务端异常重加密，覆盖父级及服务端子项。**分析：** 为受保护桶开启 CloudTrail S3 数据事件，筛选 CopyObject 中非空的客户密钥算法请求参数，并审查相关 PutObject 与分段上传。按主体、来源 IP、桶、对象键及事件时间关联，计算可调 10–30 分钟窗口内同主体覆写的既有键数量，与批准的 SSE-C 作业清单和历史桶范围比较；再核实当前版本的合法读取结果及旧版本是否保留。不得收集客户密钥本身。正常迁移/重密钥会造成误报；数据事件未启用、日志延迟或被攻陷主体本来获批使用 SSE-C 时，行为判断需要更多密钥归属与业务证据。

### Mitigation resolution candidates

`TA0040-T1486-MIT-ENDPOINT`: **candidate `extend` of MIT-000115 only for parent and sparse child**, because its existing measures already include application control, least file authority, behavior prevention, and immutable recovery. Add distinct T1486 applications: restrict unapproved writers to business directories, deploy controlled-folder protection where supported, preserve versions/canaries, and isolate a writer on confirmed multi-file readability loss even when I/O volume is low. Expected effect: blocks or constrains file-region rewrites and preserves restoration points. Limitation: approved or compromised trusted apps may write; protection only covers configured folders, and recovery copies do not prevent transient current-data outage. E6 and existing MIT-000115 source set support control concept; E2 supports the low-volume-specific application. **Do not reuse MIT-000115 wording by changing the target name.**

`TA0040-T1486-MIT-SSE-C`: **candidate `create`**, since MIT-000115 has no SSE-C policy measure. Measures: (1) explicit bucket or organization resource policy deny `s3:PutObject` when `s3:x-amz-server-side-encryption-customer-algorithm` is present, except narrowly governed application cases; (2) least-privilege, short-lived credentials and scoped CopyObject authority; (3) versioning with Object Lock or protected backups for recovery. Parent/service-child applications should state that the deny prevents attacker-supplied customer-key overwrites even when the requester has general object-write permission, while protected prior versions aid rollback if an overwrite occurs. E3 gives AWS example policy and incident; E7 describes Object Lock/versioning. Limitation: a legitimate SSE-C application needs an exception; policy does not stop a principal from client-side encrypting content and uploading a new object, and Object Lock protects a version but permits a new current version. This control is narrower than generic backup or T1490 recovery-inhibition mitigation.

## 2026-09-22 source correction: S3 SSE-C default

The service child and cloud mitigation above require a current prerequisite check. [AWS S3's current FAQ](https://docs.aws.amazon.com/AmazonS3/latest/userguide/default-s3-c-encryption-setting-faq.html) states that, after the April 2026 change, new general-purpose buckets have SSE-C disabled by default, as do existing buckets in accounts with no SSE-C-encrypted objects. Accounts with existing SSE-C objects retained their existing bucket configurations. A workload that needs SSE-C can deliberately enable it through `PutBucketEncryption`; therefore an attacker needs a bucket where it remains allowed or separate authority to change that configuration. The 2025 AWS CIRT incident report is historical evidence of the mechanism, not evidence that every S3 bucket is susceptible today. This FAQ is a new proposed reference key `TA0040-T1486-REF-SSE-C-DEFAULT` (E8).

中文：正式服务端子技术的攻击方前提应写明：目标桶允许 SSE-C，或攻击者有权先通过桶加密配置启用它。检测分析先读取每桶 `BlockedEncryptionTypes` 状态，观察解除阻止的 `PutBucketEncryption` 事件，再关联 S3 数据事件中的 SSE-C CopyObject 覆写；配置变化本身不能当作已经加密。缓解措施优先保持 AWS 现有默认阻止状态、限制 `s3:PutEncryptionConfiguration`，并对需要例外的应用收窄授权；桶/组织策略的 SSE-C 拒绝可作为纵深防护。不能把“启用 SSE-C 拒绝”写成所有新桶尚未具备的控制。恢复版本仍需要单独保护。

English: The formal service child's attacker prerequisite should say that the bucket permits SSE-C or that the actor can first enable it through bucket encryption configuration. The analytic should inventory per-bucket `BlockedEncryptionTypes`, watch `PutBucketEncryption` changes that remove the block, and then join SSE-C CopyObject overwrites in S3 data events; the configuration change alone does not establish encryption. Mitigation should preserve AWS's current default block, restrict `s3:PutEncryptionConfiguration`, and narrowly govern legitimate exceptions; an explicit bucket/organization SSE-C deny is defense in depth. Do not present SSE-C blocking as an absent control on all new buckets. Prior versions still need independent protection.

This correction supersedes any earlier phrasing in this handoff that appears to assume SSE-C is enabled for every S3 bucket. Source: [AWS S3 default SSE-C setting FAQ](https://docs.aws.amazon.com/AmazonS3/latest/userguide/default-s3-c-encryption-setting-faq.html), Important and questions 1–4.
